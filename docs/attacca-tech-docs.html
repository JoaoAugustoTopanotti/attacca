produto

visão geral

O attacca (ex-GitSong; o nome é o termo musical para "seguir ao próximo movimento sem pausa") é uma plataforma onde uma comunidade completa transcrições musicais em revezamento: uma pessoa começa uma tablatura, outra continua de onde a primeira parou, dividindo o trabalho por instrumento/trilha, com autoria de cada pedaço preservada e histórico de versões. É "GitHub para tablatura" — mas o foco não é fork/branch/merge genérico, e sim a passagem de bastão assíncrona por trilha, com player estilo Songsterr (tab multi-instrumento, trilha selecionável, playback com cursor sincronizado).

O diferencial estrutural contra o mercado (wikis convergentes como Songsterr/Ultimate Guitar, editores síncronos como Flat.io, autoria solo como Guitar Pro/MuseScore): transcrição divisível por trilha + assíncrona + autoria preservada + incompletude visível como convite. O "mural de incompletude" ("Paint It Black — 60%, falta baixo e bateria") é a resposta ao risco nº 1 do produto, a densidade: "falta baixo" só vira convite quando chega em quem toca baixo.

estado atual

  • M1 ✅ — upload de Guitar Pro/MusicXML, render + playback com alphaTab, histórico imutável de revisões com reverter.
  • M2 ✅ — formato canônico alphaTex, grade de células (trilha × compasso), edição/proposta por trilha, modelo maintainer, mural de incompletude, notificações in-app.
  • M3 ✅ — conflito de mesma célula: detecção via merge base (estilo git) + resolução humana compasso a compasso, nunca sobrescrita silenciosa.
  • Identidade durável — magic link + sessão JWT + Google OIDC (ADR 0004); e-mail verificado é a âncora da conta.
  • Editores no navegador — editor visual de tablatura (TabEditor) e step-sequencer de bateria (DrumGridEditor), ambos serializando alphaTex.
  • Primeiro revezamento real validado (26/06/2026): duas pessoas em dois computadores, proposta enviada, aceita pelo dono, snapshot no histórico — a tese central provada com gente de verdade.
princípio guia

Pequeno, nichado, provado de ponta a ponta. O projeto não compete por catálogo (800 mil músicas) nem tenta "transcrever o mundo": prova que o revezamento acontece numa comunidade pequena e densa, e só então expande. Cada mecanismo novo do produto foi provado primeiro num spike com partitura real antes de virar schema.

produto

arquitetura

A ideia central da arquitetura é o modelo mental de planilha: uma música é uma grade em que linhas são trilhas (instrumentos) e colunas são compassos. A unidade atômica de edição é a célula (trilha, compasso). Trilhas diferentes nunca colidem (merge = união, cobre ~95% do fluxo); correção em trilha alheia vira proposta estilo pull request; conflito real na mesma célula é detectado e resolvido por um humano, nunca automaticamente.

Sobre esse modelo, o pipeline de dados é uma via de mão dupla entre duas representações: o documento (alphaTex completo, que o alphaTab importa/renderiza/toca) e a grade (linhas de banco endereçáveis, onde a colaboração acontece). A verdade vive na grade; o documento é artefato derivado, remontado sob demanda e validado pelo importador oficial antes de qualquer uso.

camadas

  • src/lib/ — o domínio. Funções puras de servidor (materialização, células, trilhas, conflitos, identidade, notificações). Toda regra de negócio mora aqui; as rotas só traduzem HTTP ⇄ domínio.
  • src/app/api/ — rotas finas do App Router. Validam input, chamam a lib, mapeiam erros de domínio para status HTTP (o padrão do projeto: Error de domínio → 400 com mensagem em pt-BR; conflito M3 → 409; gates de identidade → 401/403).
  • src/components/ — client components React. O alphaTab só roda no cliente via import() dinâmico dentro de useEffect (nunca no topo do módulo — quebraria o SSR) e no servidor como pacote externo (serverExternalPackages).
decisão estrutural

O alphaTab é a única engrenagem musical do sistema: importa (ScoreLoader), exporta (AlphaTexExporter), renderiza e toca. O código do attacca nunca interpreta semanticamente alphaTex à mão — a decomposição em células (src/lib/alphatex-grid.ts) é fatiamento de texto posicional sobre um re-export anotado do próprio alphaTab, e toda validação passa pelo importador oficial. alphaTab é LGPL: usado só como dependência npm, nunca vendorizado.

as três regras de integridade que o schema impõe

  • Cascade na árvore de conteúdo, SetNull para pessoas. Apagar uma Song leva junto revisões, trilhas, compassos, células, contribuições, watches e notificações. Apagar um User não apaga conteúdo: ownerId/authorId viram null e o trabalho sobrevive anônimo.
  • A FK NoAction do aceito. Cell.acceptedContributionId → CellContribution é NoAction nos dois sentidos para evitar ciclo de cascade com CellContribution.cell (Cascade). Consequência prática: qualquer delete que alcance contribuições (delete de música, remoção de compasso, re-materialização) precisa zerar/re-apontar o ponteiro antes, na mesma transação — o padrão aparece em materialize.ts, measures.ts e no DELETE /api/songs/[id].
  • baseContributionId sem FK, de propósito. É proveniência pura (o merge base M3): pode apontar para uma linha que já não existe; null = célula estava vazia ou linha pré-M3 (falso positivo de conflito possível e aceito — só pede um olhar humano a mais).

denormalizações mantidas por código

CellContribution.authorName e Track.ownerName são caches de exibição — o vínculo real é authorId/ownerId. Renomear o usuário (PATCH /api/me) reescreve os dois caches em transação; sem isso, o nome antigo ficaria congelado nas contribuições passadas e uma pessoa leria como duas, corroendo a autoria por pedaço. Já Notification.songTitle/actorName são congelados de propósito (a notificação descreve o evento no momento em que ocorreu).

atenção · dev local

O fluxo SQLite documentado no CLAUDE.md (DATABASE_URL=file:./dev.db + prisma db push) ficou para trás: desde user_settings o schema usa String[] e Bytes, que o SQLite não suporta — o dev local precisa de um Postgres real (há docker-compose.yml no repo). persistência de arquivos e seed

Uploads não vão para disco: o blob de proveniência vive em Revision.blob (BYTEA). src/lib/storage.ts (layout storage/<songId>/<revisionId>.<ext>, com guarda de path traversal em resolveInStorage) sobrevive só para ler linhas legadas pré-blob e para limpeza best-effort no delete. O seed (prisma/seed.ts) cria 4 usuários fictícios sem e-mail e 4 músicas de domínio público — duas completas e duas com proposta pendente — usando as libs reais (materializeSongGrid, declareTrack, submitTrackContent), então todo o estado demo passa pela validação de remontagem de verdade. Para a proposta pendente nascer proposed pelo caminho real, o seed seta ownerId temporariamente e desfaz depois.

núcleo

formato canônico — alphaTex e a grade de células

ADR 0001 (2026-06-07): o formato canônico interno é o alphaTex, o formato de notação em texto do alphaTab. A decisão foi tomada com evidência de round-trip num .gp real (Stairway to Heaven: 13 trilhas, 167 compassos, 19.786 notas): o alphaTex preservou 7.551/7.551 beats-com-nota e todos os efeitos medidos (a única divergência é normalização de rests redundantes — canonicalização, não perda), é texto diffável/versionável, ~70× menor que o JSON do alphaTab (324 KB vs 22,5 MB), e o round-trip usa import/export oficiais sem nenhum código próprio. MusicXML foi descartado (o alphaTab não exporta).

conversão no upload

scoreBytesToAlphaTex(bytes) (src/lib/canonical.ts) roda 100% server-side: await import("@coderline/alphatab") (o pacote é serverExternalPackage), ScoreLoader.loadScoreFromBytes (que fareja o formato real pelos bytes — a validação de extensão em src/lib/format.ts é só gate de UX) e AlphaTexExporter().exportToString. Qualquer exceção vira null, e o caller (rota de upload) converte null em 422 sem gravar nada: não existe música aceita sem forma colaborativa.

decomposição — documento → grade

src/lib/alphatex-grid.ts é processamento de string puro, sem dependência do alphaTab — e é o mesmo código executado pelo spike de prova (spikes/assemble.ts importa de ../src/lib/alphatex-grid): o que foi provado e o que está em produção são o mesmo arquivo. O truque:

  1. O texto decomposto nunca é o alphaTex cru do usuário: importScoreFromAlphaTex (materialize.ts) importa e re-exporta com settings.exporter.comments = true, gerando um export anotado com layout linha-a-linha previsível (// Bar N / Voice, | sozinho na linha, \voice em linha própria).
  2. decompose() é uma máquina de estados (global → header da trilha → compassos): \track abre trilha; o primeiro comentário-marcador encerra o header (único uso dos marcadores); dentro dos compassos, \voice separa vozes e a linha | separa compassos. Compassos são fatiados pelo |, nunca pelos comentários (o exportador só os emite quando a estrutura muda — a ADR 0002 registra explicitamente que fatiar por marcador é frágil).
  3. toNormalized() extrai as diretivas de masterbar (\ts \tempo \section \ro \rc \ae \jump \beaming \tf \ac \ft) da trilha 0/voz 0 para Measure.structPrefix (andaime compartilhado, opaco); o corpo da célula fica com clef/ks/notas/efeitos, com as vozes daquele compasso unidas pela linha literal \voice.

                       \tuning G2 D2 A1 E1              (opaco)

nuance

A linha \voice dentro do corpo da célula não é alphaTex válido por compasso (criaria masterbars extras) — é formato interno. A remontagem transpõe: laço externo por voz, interno por compasso, re-emitindo structPrefix só na voz 0. Célula vazia remonta como r.1 (pausa de compasso inteiro) — por isso um slot recém-declarado sempre monta um documento válido. Granularidade por voz foi conscientemente descartada (ADR 0002): a célula carrega todas as vozes do compasso.

materialização — grade no banco

materializeSongGrid(songId) (src/lib/materialize.ts) pega a revisão mais recente com alphaTex, decompõe e grava a grade numa transação all-or-nothing (timeout 30 s), idempotente (substitui a grade): zera acceptedContributionId (a FK NoAction), apaga contribuições→células→trilhas→compassos, recria tudo via createMany, aponta cada célula à sua única contribuição com um UPDATE raw (sintaxe Postgres) e persiste Song.headerFragment. Colunas tipadas vêm do modelo, não do texto: ts de masterBars[m], tempo de tempoAutomations[0], instrument de playbackInfo.program, isPercussion de primaryChannel === 9. A materialização é automática no upload e no scaffold — apenas se a música ainda não tem grade; música materializada nunca é re-materializada por upload (apagaria o revezamento).

remontagem — grade → documento

assembleSongAlphaTex(songId, overrides?) remonta o documento a partir de headerFragment + structPrefix + corpo aceito de cada célula e valida importando com ScoreLoader.loadAlphaTex — retorna {alphaTex, valid, error?}. O parâmetro overrides (Map<cellId, string>) é o mecanismo universal de pré-visualização e validação sem gravar: é como propostas são ouvidas antes do aceite (GET /assembled?track=&author=), como o preview do editor funciona, e como todo aceite valida o documento inteiro antes de tocar o banco.

snapshot — o handoff no histórico

snapshotGrid(songId, authorName, message) congela o remontado como Revision kind="snapshot", creditando o autor. Dispara exclusivamente em acceptTrackProposals (proposta de outra pessoa aceita pelo dono) — não no save direto do dono, não em add/remover compasso. Decisão pós-teste real: compor do zero é save-a-save, e cada save gerando snapshot enchia o Histórico de "mudanças" que não eram passo de revezamento. É best-effort por contrato: grade que não remonta válida → null silencioso, o aceite nunca é bloqueado.

a cadeia de prova (spikes/)

  • roundtrip.mjs — fidelidade do formato (ADR 0001): contagem de notas/efeitos original × round-trip.
  • struct.mjs — fidelidade estrutural: repetições, casas alternativas, jumps, ts/ks/clef/tempo.
  • cellslice.mjs — o merge atômico: enxertar as vozes de um compasso de um score em outro + score.finish() → re-export válido, zero dano colateral.
  • assemble.ts — decompose/assemble do código de produção em 3 modos; sem perda no caso controlado e no Stairway.
  • verify-materialize.ts — pós-implementação: o GET /assembled do banco real é idêntico ao canônico da Revision (Stairway: 2.171 células).
núcleo

colaboração — trilhas, propostas e conflitos

Duas camadas: src/lib/cells.ts tem as primitivas por célula (append, aceitar, recusar, contribuidores); src/lib/track-content.ts é a UX real do produto — a pessoa edita a trilha inteira como um único alphaTex com compassos separados por |, e o submit decompõe em contribuições por célula (a granularidade de merge provada). A autoria virou por-trilha depois do primeiro teste real: célula por célula era inviável (167 compassos = 167 PRs).

invariante nº 1 · append-only

Editar uma célula = criar uma nova CellContribution + re-apontar Cell.acceptedContributionId. Nunca há UPDATE no conteúdo de uma linha existente (aceitar/recusar só muda status). A contribuição antiga vira histórico — a autoria por pedaço e o "continuar de onde o outro parou" derivam dessa regra, não de código extra.

autoridade — modelo maintainer

O dono da música é o criador (Song.ownerId, setado no POST /api/songs). O dono aceita; qualquer identificado propõe. O gate (assertCanAccept/assertOwner) compara song.ownerId com o id do ator; ownerId null (seed/legado) = música aberta, qualquer identificado salva direto. "Reivindicar trilha" foi removido (tornava o criador impotente na própria música — dor sentida no primeiro teste); Track.ownerId ficou inerte no schema para uma futura delegação. Reconhecimento vem de songContributors: dono + autores distintos de contribuições aceitas. O gate é social ("honra, não trava") e as rotas convertem violação em 400/401 com mensagem em pt-BR.

Detalhes que importam em submitTrackContent:

  • Só o que mudou vira contribuição. A comparação é normalizada (normalizeFragment: linhas trimadas, vazias fora) — o exporter indenta e o editor re-serializa sem indentação; comparação crua marcava todo compasso como mudado (o "bug dos 103 compassos", que aconteceu de verdade).
  • Contagem de compassos é imutável aqui: fragments.length !== measures.length → erro; mudar estrutura é operação separada e só-dono (measures.ts).
  • Dono (ou música aberta) → cada compasso mudado nasce accepted + repoint imediato; outro → nasce proposed. Ambos gravam baseContributionId = o aceito da célula naquele momento (o merge base).
  • Quem contribui passa a seguir a música (watchSong), e proposta de não-dono notifica o dono.

conflito de mesma célula (M3)

Detectar + humano escolhe, nunca sobrescrever em silêncio. isConflicting: conflito ⟺ o aceito atual da célula difere do baseContributionId da proposta e o conteúdo normalizado difere de verdade (conteúdo igual = sem conflito, mesmo com base diferente). O aceite em lote exige uma escolha por compasso conflitante — resolutions: Record<measure.order, "current"|"proposed">; sem escolha, UnresolvedConflictsError → HTTP 409 com os números humanos dos compassos. Escolher "current" preserva a proposta como rejected com a mensagem "conflito — o dono manteve a versão atual do compasso"; todas-"current" vira recusa total (sem snapshot). Re-propor grava base novo e desfaz o conflito naturalmente; em re-proposta na mesma célula, a mais nova vence (orderBy createdAt asc + sobrescrita em Map). A UI mostra os dois lados como tablatura renderizada (TabSnippet), não texto.

completude e o mural

Dois tipos de incompletude: a lacuna dentro da trilha (a grade já dá) e a trilha ausente ("falta baixo"), que exige instrumentação declarada. declareTrack (src/lib/tracks.ts) cria uma trilha-slot que nasce vazia e sem dono — uma Cell por compasso, sem contribuição — e o slot vazio é o convite. songCompleteness mede pelo critério honesto: célula pronta ⟺ acceptedContributionId != null (pausa transcrita conta — silêncio é música); slot novo lê 0%, import cheio lê 100%; missing = trilhas com done === 0. O match trilha ↔ "instrumentos que eu toco" é por família GM (instrumentLabel, 16 famílias de 8 programas — guitarra num .gp costuma vir program 29, não 25), via presetFamily.

estrutura de compassos

addMeasure/deleteMeasure (src/lib/measures.ts) inserem/removem uma coluna inteira, só o dono, sem snapshot. O deslocamento de order respeita o @@unique([songId, order]) (de trás pra frente ao abrir espaço, da frente pra trás ao fechar). Remoção é bloqueada no último compasso e em compasso com structPrefix (carrega fórmula/seção/repetição). O delete zera acceptedContributionId da coluna antes de apagar (a FK NoAction, de novo).

diff de propostas

src/lib/linediff.ts: LCS clássico O(n·m) por programação dinâmica, zero dependências, com a mesma normalização de linhas do submit. diffRows colapsa trechos iguais em {type:"gap"} com 2 linhas de contexto; diffStat dá o "+N −M" do cabeçalho. No painel de propostas o diff também é pintado na partitura: os beats mudados (LCS de assinaturas de beat) viram highlightBeats verdes no AlphaTabPlayer.

identidade & auth

ADR 0004: a âncora da identidade é o e-mail verificado (User.email @unique + emailVerified), não o cookie. Perder o cookie não perde a conta — reautentica-se pelo e-mail e cai no mesmo User, preservando a autoria por pedaço (o diferencial do produto). Não há senha nem next-auth: login passwordless por magic link + sessão JWT, e Google como segundo autenticador hand-rolled (~100 linhas), ambos convergindo na mesma função de resolução.

magic link

  1. POST /api/auth/request valida o e-mail (regex, trim + lowercase) e chama issueLoginToken (src/lib/identity.ts): token raw = randomBytes(32) base64url; só o SHA-256 é persistido (LoginToken.tokenHash); TTL 30 min. O raw vive apenas na URL enviada por e-mail (e no devUrl da resposta, só sem provider e fora de produção).
  2. GET /api/auth/verify?token= consome: acha por hash, rejeita consumido/vencido (redirect /?auth_error=invalid|expired), resolve o usuário e queima todos os tokens pendentes do mesmo e-mail. Sempre responde redirect 307, nunca JSON.
  3. resolveUserForEmail é o único lugar do código onde um e-mail verificado vira conta. Ordem de resolução: (1) e-mail já conhecido → aquela conta; (2) claimUserId → anexa o e-mail in place a uma conta existente (ponte do cookie legado gs_uid e troca de e-mail — mesmo User.id, autoria intacta); (3) cria conta nova (displayName proposto ou derivado do local-part). A regra "(1) vence (2)" garante que provar posse de um e-mail já usado loga naquela conta em vez de movê-lo.
  4. Sessão: JWT HS256 via jose (sub=userId, exp 30 dias) no cookie httpOnly gs_session. getCurrentUser() verifica o JWT e carrega o User — é a única porta de identidade das rotas (a assinatura foi preservada desde a era do cookie, por isso nenhuma rota consumidora mudou). Logout só limpa o cookie; não há revogação server-side (fora de escopo por ADR).

google (OIDC + PKCE)

Authorization code + PKCE S256, com state/code_verifier/redirect em cookies httpOnly de 10 min. O callback troca o code no token endpoint e verifica o id_token contra o JWKS remoto do Google (jose: assinatura + iss nas duas formas + aud = client id); email_verified !== true é recusado — senão alguém reivindicaria conta de endereço que não controla. O e-mail resolvido passa pelo mesmo resolveUserForEmail, então Google + magic link no mesmo endereço = mesma conta (provado, sem duplicar). Sem GOOGLE_CLIENT_ID/SECRET, /api/auth/providers devolve {google:false} e o modal esconde o botão. Todos os erros do fluxo saem como redirect /?auth_error=google_*, que o IdentityWidget mapeia e reabre o modal com a razão.

perfil e conta

  • Renomear (PATCH /api/me → updateProfile): nome trimado 2–40 chars; se mudou, reescreve os caches denormalizados CellContribution.authorName + Track.ownerName em transação. No cliente, emitMeChanged (src/lib/identity-events.ts, um CustomEvent gs:me-changed) atualiza o header sem F5.
  • Trocar e-mail (POST /api/me/email): 409 se o endereço pertence a outra conta; emite magic link para a caixa nova com claimUserId=eu e redirectTo=/settings?email=changed — nada muda até o link ser aberto; prova de posse obrigatória.
  • Instrumentos (User.instruments String[], chaves de INSTRUMENT_PRESETS): alimentam o destaque "precisa do seu instrumento" no mural.
  • Overview (GET /api/me/overview): o inbox do revezamento — esperando por você / propostas em aberto / minhas músicas / seguindo.
segurança · o que existe e o que não

Existe: hash-only do token, uso único + queima de concorrentes, TTL, JWT httpOnly/lax/secure-em-prod, anti open-redirect (safeRedirectPath: só paths começando com / e não //), verificação completa do id_token, HMAC + timingSafeEqual no cookie legado, e-mail sempre normalizado. Não existe (fora de escopo declarado na ADR 0004): rate-limit no request, anti-enumeração, revogação de sessão server-side, senha. O segredo do JWT cai em cascata GS_AUTH_SECRET ?? GS_COOKIE_SECRET ?? "dev-insecure-change-me" — em produção as envs devem estar setadas.

AlphaTabPlayer — toda a integração alphaTab num componente

  • Import dinâmico obrigatório: await import("@coderline/alphatab") dentro do useEffect, nunca no topo do módulo (quebraria o SSR). Settings: core.fontDirectory="/font/", player.soundFont="/soundfont/sonivox.sf2", cursor + ScrollMode.Continuous, display.resources = alphaTabResources(readTheme()) — o alphaTab desenha em canvas/SVG próprio e não herda CSS; as cores da tablatura vêm por objeto, por tema.

  • Percussão: StaveProfile.Tab puro quebra o layout do alphaTab 1.8.3 em trilha de bateria ("Cannot read properties of undefined (reading 'staves')") — applyStaveProfileFor aplica o perfil por trilha (percussão → ScoreTab; demais → preferência da pessoa) e todo scoreLoaded normaliza bar.clef = Clef.Neutral nas pautas de percussão (o importer alphaTex deixa clave de sol).
  • Diff na partitura: a prop highlightBeats: string[] (formato "measureIndex:beatIndex", voz 0) pinta de verde os beats/notas mudados via NoteStyle/BeatStyle (sub-elementos de tab e de notação standard) antes do renderTracks.
  • Preferências vivas: src/lib/player-prefs.ts guarda notação/zoom/velocidade/volume/metrônomo/contagem em localStorage (gs.player.prefs — "descrevem um aparelho, não uma identidade"); writePlayerPrefs dispara um CustomEvent que players montados aplicam na hora (áudio ao vivo; escala/pauta exigem updateSettings() + render()).

o player mostra a verdade viva

SongTabs detecta materialização via GET /completeness (tracks.length > 0) e então view = "live": o PlayerPanel toca /api/songs/[id]/assembled — o remontado das células, todas as trilhas — e não o snapshot de upload. "Ouvir" no HistoryPanel troca a key do player (remontagem completa da instância) e mostra a barra "Tocando a versão #N — ← Voltar ao atual". ProposalsPanel — a tela de revisão

Fila agrupada por (trilha, autor); dono vê todas, colaborador vê as suas (filtro de UI — a rota é pública; o servidor re-valida no aceite). O detalhe abre em tela cheia com: contagem +N −M (diffStat), tablatura com os beats mudados em verde (highlights por LCS de assinaturas JSON de beat, via parseTrackTex — comparação normalizada, nunca texto cru), player "ouvir como fica" (/assembled?track=&author=, proposta aplicada em memória, abrindo na trilha via defaultTrackIndex) e, no M3, os conflitos por compasso lado a lado: dois painéis clicáveis "na música agora" × "proposta de X", renderizados como tablatura por TabSnippet (instância alphaTab render-only, sem player/soundfont; pointer-events:none para o clique cair no botão). conflictBarTex injeta \ts quando o structPrefix não o traz — um compasso solto sem fórmula leria 4/4. Aceitar fica desabilitado até todo conflito ter escolha; o servidor devolve 409 de qualquer forma (defesa em profundidade).

frontend

editores — tablatura visual e bateria em grade

Duas libs puras (zero DOM, testáveis em Node) com o mesmo contrato — parse → modelo imutável → mutações que retornam modelo novo → serialização round-trip estável, preservando opaco tudo que o editor não modela (sufixos de nota/beat, diretivas \clef/\ks como prefixo, vozes 1+ como tail, bends importados). Dois componentes de UI com o mesmo handle (TabEditorHandle { seekTick }) e a mesma convenção de eco (lastEmittedRef distingue mudança externa — refetch pós-save — do eco da própria edição). O TrackEditor orquestra: carrega GET .../content, escolhe o editor por track.isPercussion, mantém o buffer, salva/propõe por POST .../content.

alphatex-editor.ts + TabEditor (instrumentos de corda)

  • Gramática do beat: casa.corda{efeitosDeNota}.duração{efeitosDeBeat}; pausa r.dur; acorde (c.s c.s).dur. Efeitos de nota vêm antes da duração; anotações de beat depois; o alphaTab aceita um único grupo {} por nota e por beat — o serializer mescla efeitos editáveis + anotações opacas num grupo só.
  • Pegadinha nº 1 — numeração de corda: alphaTex numera corda 1 = mais aguda; o modelo do alphaTab numera 1 = mais grave. Conversão obrigatória tex = total + 1 − model em todo clique/overlay.
  • Formato de submissão ≠ formato de render: serializeModel produz o formato de célula (vozes dentro do compasso); \voice por compasso não é alphaTex válido (cria masterbars extras). Renderizar usa serializeForRender (vozes transpostas + trackHeader + structPrefix) → mesmo número de masterbars da música completa, senão cliques e ticks desalinham.
  • Capacidade do compasso em 64avos, fracionária: pontuado ×1.5/×1.75, quiáltera den(N)/N ou M/N, grace ×0. wouldOverflow bloqueia só o que aumenta além da fórmula; badges "falta/passa X" na tablatura.
  • Interações: clique escolhe corda pelo Y (geometria calibrada por NoteBounds); dígitos com acúmulo de 2 dígitos (900 ms, casas ≤ 24); seleção âncora↔cursor (Shift+setas/clique, Ctrl+Shift+←→ por compasso); clipboard Ctrl+C/X/V em escopo de módulo (copia entre trilhas/músicas); Ctrl+D repete a seleção adiante; Alt+←→ move o beat no tempo (atravessa compasso); Shift+↑↓ move a nota de corda; +/− duração; ./Ctrl+. pontuado; Ctrl+Z/Y undo/redo (pilha ≤200, zerada em mudança externa). Convenções emprestadas do nicho (GP8/Soundslice/MuseScore/TuxGuitar).
  • Percussão nunca entra no TabEditor visual (prop percussion força modo texto e o alphaTab nem inicializa) — a rota normal é o DrumGridEditor.

drum-grid.ts + DrumGridEditor (percussão)

  • Modelo step-sequencer: linhas = peças do kit (MIDI GM: 36 bumbo, 38 caixa, 42 chimbal…), colunas = subdivisões por fórmula (resolução 1/4..1/32), quiáltera por tempo, pincéis nota/acento/fantasma/flam. Serializa alphaTex numérico por compasso: (36{ac} 42).16{tu 3}; flam = acorde de graça {gr} antes do golpe; NAME_TO_MIDI confere 1:1 com as articulações do alphaTab 1.8.3 (round-trip de trilha importada).
  • Anti-ruído de diff: compasso não tocado re-emite o texto original (origsRef) — um clique numa célula não re-serializa a trilha inteira (o "bug dos 103 compassos" reapareceria aqui). Diretivas iniciais viram prefixo opaco posicional que não viaja com conteúdo copiado.
  • Fallbacks conscientes: \voice (2 vozes — padrão em bateria de .gp), ritmo pontuado ou subdivisão irregular → modo texto com guia de notação. Baixar a resolução move golpes (destrutivo) → remapBeatIsLossless detecta e pede confirmação.
  • Entrada rápida (benchmark FL Studio/Hydrogen): arrastar pinta a linha (estado-alvo decidido na 1ª célula; o arrasto lê barsRef, não o state), botão direito apaga, menu na peça preenche "a cada tempo/½ tempo/célula", seleção de compassos + Ctrl+C/X/V/D com conformBar (colar conforma cada compasso à fórmula/resolução do destino), undo com snapshot que inclui a resolução. Um arrasto = um passo de undo.

a tela /edit

O playback é um AlphaTabPlayer headless (editMode audioOnly) tocando o /assembled — a música completa, não só a trilha editada. Cursor bidirecional por tick (semínima alphaTab = 960 → semibreve = 3840, o mesmo TPW da drum-grid): onTickChange do player → editorRef.seekTick; clique num beat do editor → playerRef.seekTick. "Play toca o que se vê": com edição não salva, POST .../preview monta o documento com a trilha local aplicada e o player recarrega via loadTex — nada é gravado. Após propor, o buffer não é recarregado (recarregar revertia a tela para a versão aceita e a edição "sumia"). Add/remover compasso salva o buffer dirty primeiro — nunca descarta edição pendente. CellEditor.tsx (edição por célula) é legado sem importadores.

frontend

shell, tema & home

tema — dark first, anti-flash

O <html> sai do SSR com data-theme="dark"; um script inline (primeiro nó do body em layout.tsx) promove para light antes da pintura apenas se localStorage["attacca:theme"] === "light" — zero flash, e qualquer erro cai em dark. Tokens em :root de globals.css (carvão #141311, texto #ede9e2, vermelhão #e5432b = "a sua vez"/a lacuna — o acento não muda entre temas), override em [data-theme="light"] (papel #fcfbf8, tinta #141414). src/lib/theme.ts: readTheme/applyTheme + alphaTabResources(theme) — a ponte de cores para o canvas do alphaTab. Fontes via next/font (Space Grotesk títulos, Inter texto, JetBrains Mono dados). Assinatura visual: .blockbar — 14 blocos, tinta = feito, vermelhão = borda viva, cinza = não começou.

globals.css como contrato

Um único stylesheet global (2.377 linhas) — sem CSS Modules/Tailwind; cada componente tem sua família de classes por prefixo (.tab-editor-*, .drum-*, .mural-*…). Três contratos que não são decoração:

  • .at-cursor-bar/.at-cursor-beat/.at-selection/.at-highlight — "DO NOT REMOVE": o alphaTab injeta os elementos do cursor de playback sem estilo nenhum; sem essas regras o cursor é invisível (bug real do histórico). Como usam var(--accent), cursor/seleção seguem a troca de tema ao vivo — diferente da tablatura (canvas), que só muda via alphaTabResources na remontagem.
  • Casca de modal única: .auth-overlay/.auth-modal é compartilhada por AuthModal, DeleteSongButton (.danger-modal) e WelcomeInstrumentsModal — modal novo = casca + modificador, nunca outra estrutura de overlay.
  • Cor = significado, imposto pelos tokens: o vermelhão marca exclusivamente "a sua vez"/a lacuna (tab ativa, badge, borda viva da blockbar, chip "precisa de você", cursor); o botão padrão é tinta invertida (bg var(--text)), nunca vermelhão. Estados derivados por color-mix dos tokens — o mesmo CSS serve aos dois temas. Não há prefers-color-scheme: o tema é 100% [data-theme] + localStorage.

home = mural

page.tsx (server, force-dynamic) calcula songCompleteness por música e divide em Tocar (grade existente e ≥ 80%) × Colaborar. Cada item leva as famílias GM derivadas das trilhas (families/openFamilies/missingFamilies). HomeTabs (client) aplica busca acento-insensível (NFD + strip), chips por família (só de famílias presentes — "filtro morto não é filtro"), e o destaque "precisa de você": missingFamilies ∩ instrumentos declarados, calculado no cliente (editar as tags na home atualiza sem refetch); a aba Colaborar ordena essas músicas primeiro — a alavanca contra o risco de densidade. Linha do mural: BlockBar + "falta alguém em: X" + CTA por estado ("Tocar →" / "Assumir →" / "Continuar daqui →").

criar música e login no meio do caminho

/songs/new tem três modos (do zero — default, template attacca, upload). O POST /api/songs exige identidade; o 401 é tratado como convite: o form salva rascunho em sessionStorage (attacca:new-song-draft), abre o AuthModal (Google → divisor "ou" → magic link, degradando conforme GET /api/auth/providers) e restaura o formulário na volta do login. Depois: modo upload → POST /revisions; do zero/template → POST /scaffold → direto no /edit. Primeiro login com ?welcome=1 e conta sem instrumentos abre o WelcomeInstrumentsModal ("o que você toca?") — alimenta o mural. Todos os modais (auth, welcome, exclusão) reusam a mesma casca .auth-overlay/.auth-modal via portal, com Esc/backdrop fechando e scroll do body travado.

O modelo geral é "escrever exige identidade", mas seis escritas fogem da regra (resquícios do M1 ou decisões de fricção mínima): upload de revisão, revert, scaffold, preview, materialize e declarar slot aceitam anônimo. Duas delas merecem atenção: POST /materialize é destrutivo em música viva (apaga e recria a grade — o guard "só sem grade" vive nos callers, não na rota) e POST /revert não tem gate no servidor (o botão some da UI para não-donos, mas a rota aceita qualquer um). Candidatas óbvias a endurecimento antes de abrir o produto.

build & deploy

build — por que --webpack

O alphaTab precisa de Web Workers, Audio Worklets e assets estáticos (fonte Bravura, soundfont SONiVOX). O plugin oficial @coderline/alphatab-webpack resolve tudo isso, mas é de webpack — então next dev/next build rodam com --webpack (não o Turbopack padrão do Next 16). Em next.config.mjs: o plugin entra só no client build (!isServer) com assetOutputDir: public/ (o Next serve /font/ e /soundfont/ — gitignored, gerados, nunca commitar); serverExternalPackages: ["@coderline/alphatab"] mantém o pacote fora do bundle do servidor, onde ele roda como módulo Node puro para o canônico.

npm run dev     # next dev --webpack -p 4000
npm run build   # prisma generate && next build --webpack
npm start       # next start -p ${PORT:-4000}  (expansão POSIX — Render/Linux)
npm run db:seed # tsx prisma/seed.ts

dev local

Postgres via docker-compose.yml: postgres:16, porta 55432 (evita colisão com Postgres nativos), credenciais attacca/attacca/attacca_dev, e name: attacca fixado de propósito — sem isso, renomear a pasta (ainda GitSong) criaria volume novo e o banco dev "sumiria". DATABASE_URL=postgresql://attacca:attacca@localhost:55432/attacca_dev. Sob TLS corporativo, NODE_OPTIONS=--use-system-ca resolve UNABLE_TO_VERIFY_LEAF_SIGNATURE. Após mudar o schema, reiniciar o next dev (client Prisma em memória fica velho → 500).

Free tier do Render tem cold start — os forms mostram "servidor acordando" após 10 s.

invariantes & pegadinhas

O checklist do que não pode quebrar — as regras que várias partes do código assumem — e as armadilhas conhecidas, todas observadas no código real.

invariantes (quebrar = corromper o produto)

  • Append-only em CellContribution: nunca UPDATE em conteúdo; editar = linha nova + repoint; recusar = status. A autoria por pedaço deriva disso.
  • Documento sempre válido: todo aceite/save remonta a música inteira com os candidatos como overrides e importa no alphaTab antes de gravar.
  • Zerar acceptedContributionId antes de deletar contribuições (FK NoAction) — padrão obrigatório em delete de música, remoção de compasso e re-materialização.
  • Música com grade nunca é re-materializada pelo fluxo normal — re-materializar apaga o revezamento.
  • Histórico imutável: reverter cria revisão nova; snapshot só no aceite de proposta de terceiro (o handoff), nunca em save direto ou operação estrutural.
  • Comparações de fragmento sempre normalizadas (linhas trimadas, vazias fora) — em submit, conflito e diff. Comparação crua = "bug dos 103 compassos".
  • Conflito M3 nunca se resolve sozinho: escolha humana por compasso ou 409.
  • alphaTab nunca no topo de módulo client (import dinâmico no useEffect); no servidor, sempre via serverExternalPackages; nunca parsear alphaTex semanticamente à mão.
  • Percussão nunca renderiza com StaveProfile.Tab; clave normalizada para neutra em todo scoreLoaded.
  • A surface do alphaTab nunca sai do DOM enquanto a instância vive (headless = fora da tela, não desmontada).
  • Corda alphaTex (1 = aguda) ≠ corda do modelo alphaTab (1 = grave): conversão tex = total + 1 − model em todo ponto de contato.
  • Renomear usuário reescreve os caches authorName/ownerName — o vínculo real é o id.
  • Notificações/e-mail best-effort: nunca podem falhar a ação de domínio.
  • Denormalizações de Notification são congeladas de propósito; as de autoria não.

pegadinhas conhecidas (dívidas conscientes e armadilhas)

  • POST /materialize sem auth nem guarda e POST /revert sem gate no servidor — os buracos mais sérios da matriz de autorização (gate só na UI).
  • Violação de gate sai como 400, não 403 (os gates lançam Error comum): cliente não distingue "sem permissão" de "input inválido" pelo status.
  • Atomicidade desigual: acceptContribution/acceptTrackProposals são transacionais, mas submitTrackContent grava num loop sem transação e addCellContribution faz create + repoint em duas chamadas; upload + materialização usam compensação manual (delete no catch).
  • Sequências calculadas fora de transação (Revision.number, slug): corrida termina em erro barulhento no unique, não em corrupção — mas termina em erro.
  • baseContributionId null (linhas pré-M3) pode dar falso positivo de conflito — seguro, só pede um olhar humano.
  • Dev local: o schema atual (String[], Bytes) não roda mais em SQLite, apesar do CLAUDE.md/.env.example ainda citarem dev.db; use o Postgres do docker-compose.
  • Trocar o tema não repinta players alphaTab já montados (alphaTabResources é lido na montagem); prefs de player têm evento vivo, tema não.
  • globals.css referencia var(--fg) em .btn-secondary/.btn-ghost, token que nunca é definido (o correto é --text).
  • INSTRUMENT_PRESETS é importado por dois caminhos (@/lib/tracks re-exporta @/lib/instrument-presets) — mesmo objeto, mas confira antes de mexer.
  • Doc-comments desatualizados: deleteMeasure ("registrado no histórico" — não gera snapshot) e a rota /materialize ("not wired into uploads yet" — upload já materializa).
  • Rascunho de /songs/new vive em sessionStorage: sobrevive ao login na mesma aba, morre se o magic link abrir em outra.
  • saveRevisionFile (storage.ts) é órfã de propósito (o upload grava blob no banco desde 2026-06-16) — não "religar" achando que é código morto por acidente.
  • Warning de hidratação: testar primeiro em janela anônima (extensão Bitdefender injeta atributos pré-hidratação; é o motivo do suppressHydrationWarning no layout).
  • Remover as regras .at-* do globals.css deixa o cursor de playback invisível (o alphaTab injeta os elementos sem estilo).
  • playWhenReady do editor é um poll de ~6 s sobre o soundfont — se demorar mais, o play silenciosamente não acontece.
  • Fora de escopo declarado (ADR 0004): rate-limit no request de login, anti-enumeração, revogação server-side de sessão, exclusão de conta (o caminho será anonimizar — o histórico imutável não permite apagar).
  • Limites atuais do editor: vozes 1+ são opacas (edita-se a voz 0); bateria com 2 vozes cai para modo texto; add/remover compasso é só do dono (estrutural-como-proposta precisa de design próprio — compassos têm identidade por id, insert+delete ≠ edição).
